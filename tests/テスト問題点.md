## Facade の内部フィールドへ依存するテスト
- 該当: `tests/presentation/viewModels.test.js`
  ```js
  const worldRepository = {
    getWorld: vi.fn(async () => createWorld()),
    saveWorld: vi.fn(async () => {})
  };
  const editFeatureUseCase = { _worldRepository: worldRepository };
  ```
  `EditFeatureUseCase` の内部フィールド `_worldRepository` を直接 stub 化しており、Facade の実装詳細に縛られている。イベント通知や公開メソッドの戻り値で挙動を検証する作りにしないと、内部構造の変更でテストが壊れる。
- 該当テストケース: `tests/presentation/viewModels.test.js` の `it("loads world data and exposes only visible features")`

- Facade 内部の該当フィールド (`src/application/usecases/EditFeatureUseCase.js`)
  ```js
  constructor(worldRepository, geometryService, layerService, polygonEditService, idGenerationService) {
    this._worldRepository = worldRepository;
    ...
  }
  ```
  `_worldRepository` は内部状態として保持されているだけで、外部から直接差し替える契約は存在しない。テスト側が無理に触れると保守性が低下する。
- 該当実装箇所:
  - `src/presentation/view-models/MapViewModel.js` のコンストラクタ（依存を受け取って保持）
  - 同ファイルの `loadWorld`（`EditFeatureUseCase` の公開 API を利用する想定）
- 想定される副作用  
  - 実装側で `_worldRepository` を `#worldRepository` といったクラスフィールドに変更、または `EditFeatureUseCase` が内部で別のラッパーを保持するようになった場合、テストは即座に失敗する。  
  - `MapViewModel` の初期化ロジックが `editFeatureUseCase` のメソッドを直接呼び出すように変わると、`_worldRepository` を差し替えてもロード処理がスタブを通らなくなる。  
  - イベント駆動で `MapViewModel` が `worldRepository` とは非同期にやり取りする設計へ移行した際、テストが現在の同期フローを前提にしているとレースコンディションが露見しない。
- 見直し指針  
  - 世界データ読込の成功は `viewModel.getFeatures()` やイベント通知 (`eventBus.publish`) の結果で検証し、リポジトリ stub は `EditFeatureUseCase` の公開 API を通じて供給する。  
  - `MapViewModel` のテストでは `EditFeatureUseCase` 用のスタブに `addFeature` / `deleteFeature` 等のメソッドを用意し、`_worldRepository` には触れずに挙動を観察する。

## EditFeatureUseCase の実装詳細依存
- 委譲先を直接差し替えるテスト (`tests/application/editFeatureUseCase.test.js`)
  ```js
  const useCase = new EditFeatureUseCase(
    worldRepository,
    geometryService,
    layerService,
    polygonEditService,
    idService
  );

  useCase._addFeatureUseCase = { execute: vi.fn().mockResolvedValue({ id: "added" }) };
  useCase._updateFeatureUseCase = { execute: vi.fn().mockResolvedValue({ id: "feature-1", name: "Updated" }) };
  useCase._deleteFeatureUseCase = { execute: vi.fn().mockResolvedValue(undefined) };
  useCase._vertexEditUseCase = { moveVertices: vi.fn().mockResolvedValue({ updated: true }) };
  ```
  非公開フィールドに直接アクセスして委譲の呼び出し回数だけを確認している。Facade の内部構成が変わった場合に即座にテストが失敗する。
- 該当テストケース:
  - `tests/application/editFeatureUseCase.test.js` の `it("dispatches to AddFeatureUseCase for creation")`
  - 同ファイルの `it("forwards updates to UpdateFeatureUseCase")`
  - 同ファイルの `it("forwards deletions to DeleteFeatureUseCase")`
  - 同ファイルの `it("routes vertex movement through VertexEditUseCase")`

- Facade が依存を自前で生成している実装 (`src/application/usecases/EditFeatureUseCase.js`)
  ```js
  this._addFeatureUseCase = new AddFeatureUseCase(
    worldRepository, geometryService, layerService,
    this._generateIdFunc, this._processGeometryFunc, this._getVerticesFromIdsFunc
  );
  this._updateFeatureUseCase = new UpdateFeatureUseCase(
    worldRepository, geometryService, layerService,
    this._processGeometryFunc, this._getVerticesFromIdsFunc,
    polygonEditService
  );
  this._deleteFeatureUseCase = new DeleteFeatureUseCase(
    worldRepository,
    this._cleanupUnusedVerticesFunc
  );
  this._vertexEditUseCase = new VertexEditUseCase(
    worldRepository, geometryService,
    this._cleanupUnusedVerticesFunc,
    this._generateIdFunc, this._getOlderVertexIdFunc,
    layerService
  );
  ```
  委譲先を内部で new しているため、テストは公開 API を通じて結果を検証するか、依存差し替え用の仕組みを設計として用意しない限り保守性が担保できない。
- 該当実装箇所:
  - `src/application/usecases/EditFeatureUseCase.js` のコンストラクタ（委譲先 UseCase を new して内部保持）
  - 同ファイル内の各公開メソッド（`addFeature` / `updateFeature` / `deleteFeature` / `moveVertices`）が内部委譲へ接続
- 詳細な問題点  
  - `EditFeatureUseCase` はコンストラクタで `new Date().getTime()` を利用する `generateId` 委譲等を内部生成するため、テストが `_addFeatureUseCase` を差し替えても ID 発行や Geometry 処理の副作用が残存する可能性がある。  
  - 実装が将来、委譲先を `Map` に保持したり、ファクトリ関数に切り出した場合、テストは内部構造を直接再設定できず、委譲確認そのものが不可能になる。  
- 推奨される修正方針  
  1. `_addFeatureUseCase` など private フィールドにアクセスせず、`useCase.addFeature` 等の公開メソッドに対して「世界の変化」「返り値」「イベント発火」を検証する end-to-end 形式へ置き換える。  
  2. どうしても委譲を監視したい場合は、実装に「依存差し替え用のオプション引数」を公式に追加し、その契約をテストでも利用する。テストはその契約を通じてのみ差し替えを行い、 private フィールド名の直接参照を廃止する。
## PropertiesTabView の選択状態が未検証
- サイドバーの `PropertiesTabView` に複数選択や所有者不明のメッセージ分岐を追加したが、DOM を介した表示切り替えを確認するテストが存在しない。
- 状態分岐の実装 (`src/presentation/views/sidebar/PropertiesTabView.js:51-78`)
  ```js
  if (!featureForProperties) {
    if (ownerIdList.length > 1) {
      this._renderMultiSelectionMessage(ownerIdList);
    } else if (hasVertexSelection && ownerIdList.length === 0) {
      this._renderAmbiguousSelectionMessage();
    } else {
      this._renderNoSelectionMessage();
    }
    return;
  }
  ```
  仕様上は 3 種類の空状態メッセージを出し分ける必要があるが、`update()` を呼び出した結果の DOM を検証するテストがないため退行を検知できない。
- 課題:
  1. `MapViewModel` 依存の戻り値を制御できるテストダブルが整備されていない。
  2. JSDOM / Happy DOM など DOM を提供するテスト環境をプロジェクト共通で有効化していない。
- 対応案:
  1. Vitest の `environment: "jsdom"` を利用し、`PropertiesTabView` に渡す ViewModel モックを用意して各分岐を `querySelector` で検証する。
  2. または状態判定を純関数へ抽出し、`{ mode: 'multi', owners: [...] }` のような戻り値をユニットテストで保証した上で、DOM ブロックはスナップショットまたは最小限のレンダリングテストに留める。
