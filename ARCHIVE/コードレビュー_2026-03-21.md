## 強み

### 1. アーキテクチャ設計 — 本物のDDD実装

多くのプロジェクトがDDDを「名乗るだけ」で終わるなか、このプロジェクトは実際に機能している。

- Domain層はフレームワークに一切依存していない
- `FeatureAnchor` の設計が特に優秀 — 「時刻インデックス付き状態」というドメイン概念をValue Objectとして正確に表現している
- DIコンテナ (`src/main/DependencyInjection.js`) がシンプルで見通しがよい

### 2. 不変性の徹底

```js
// FeatureAnchor.js
this._shape = deepFreeze(deepClone(data.shape || {}));
Object.freeze(this);
```

`deepFreeze` + `deepClone` を使い、Value Objectが外部から変更不能になっている。
`withX()` メソッドで新インスタンスを返すパターンも一貫している。

### 3. テストカバレッジ — 50+ファイル

Domain / Application / Infrastructure / Presentation の全層にテストがある。
特に Presentation層のViewModel テストは珍しく、かつ実際に意味がある。

## 問題点

### 1. TypeScriptを使っていない — 最大の技術的リスク

このプロジェクトの複雑さ（エンティティ継承ツリー、時系列状態管理、コマンドパターン）は、型安全性の恩恵が最も大きいケースだ。

```js
// IPolygonEditService.js — これは「インターフェース」ではなく、ただのドキュメント
async validatePolygonRings(polygon, world) {
  throw new Error("Method 'validatePolygonRings' not implemented.");
}
```

実装側が `IPolygonEditService` を継承し忘れてもエラーにならない。

### 2. リファクタリング途中の残骸

```js
// DependencyInjection.js:112
this._container.historyService = new HistoryService(
    this._container.historyStackManager,
    this._container.historySerializer,
    null,          // ← 削除されたoperationEngineのnull渡し
    ...
);

// HistoryService.js:23
_operationEngine; // 最終的に削除される  ← いつ削除するのか？
```

`Feature.js` の `void properties`（後方互換引数）、`getPropertyAt`（「後方互換メソッド」なのに `@deprecated` タグなし）など、リファクタリングが「途中で止まった」痕跡が複数ある。

### 3. 神オブジェクト（God Object）

| ファイル                                       | サイズ             | 問題                                   |
| ---------------------------------------------- | ------------------ | -------------------------------------- |
| `src/infrastructure/rendering/SVGRenderer.js`  | 57KB               | 描画・変換・ラベリング・スタイルが混在 |
| `src/presentation/view-models/MapViewModel.js` | 36KB               | 状態管理の責務が広すぎる               |
| EditingViewModel系                             | ~80KB（4ファイル） | ファイル分割で対処しているが根本は同じ |

### 4. DI内のハードコード

```js
// DependencyInjection.js:72
const worldWidth = 360; // ConfigManagerから取得する方が望ましい
```

自分で「望ましくない」と書いておきながら残している。

## 実装者Codexからの返信

レビューありがとうございます。強みとして挙げていただいた「Domain層の独立性」「`FeatureAnchor` の不変性」「全層にまたがるテスト整備」は、こちらも重視して進めてきた点であり、認識は一致しています。

### 受ける指摘

- `HistoryService` の `_operationEngine` は実際に残骸です。`src/main/DependencyInjection.js` では `null, // operationEngine は null を渡す`、`src/application/services/HistoryService.js` では `_operationEngine; // 最終的に削除される` となっており、この契約は整理対象です。
- `src/infrastructure/rendering/SVGRenderer.js`、`src/presentation/view-models/MapViewModel.js`、`src/presentation/view-models/EditingViewModelDragging.js` が大きい点も妥当な指摘です。責務境界をさらに切り出す余地があります。

### 前提が少し異なる指摘

- `src/domain/entities/Feature.js` の `void properties` / `getPropertyAt` は「途中で止まった死骸」というより、履歴アンカー移行中の互換レイヤーです。実際に `Feature.js` には `getPropertyAt(timePoint) { return this.getAnchorAt(timePoint); }` があり、現状でも `src/infrastructure/rendering/SVGRenderer.js`、`src/presentation/views/MapView.js`、`src/presentation/views/sidebar/FeaturesTabView.js`、`src/presentation/views/sidebar/PropertiesTabView.js`、および複数テストから参照されています。したがって課題は「未削除」そのものではなく、「互換レイヤーであることの明示不足」です。`@deprecated` の付与と置換先の統一は進めます。
- `src/main/DependencyInjection.js` の `const worldWidth = 360;` は、単なる思いつきのハードコードではなく、現行の世界地図座標系の契約値です。`src/infrastructure/rendering/ViewportManager.js` でも `worldWidth: options.worldWidth || 360 // 地図のワールド座標幅を追加`、`src/infrastructure/rendering/SVGRenderer.js` でも `worldWidth: 360, // ワールド座標系での背景地図の幅 (経度360度分)` として前提化しています。設定化自体は妥当ですが、単独の定数移動ではなく、描画・ラップ計算・ヒット判定まで含めた契約整理として扱うべき箇所です。
- TypeScript については有効性を否定しませんが、短期 ROI が最も高い施策とは見ていません。現状でも `src/domain/entities/Feature.js` は `Feature ${id} requires at least one FeatureAnchor.` を強制し、`src/domain/value-objects/FeatureAnchor.js` は `deepFreeze(deepClone(...))` と `Object.freeze(this)` で不変条件を固定し、`src/application/services/PolygonEditService.js` もコンストラクタで依存を検証しています。まずは未使用契約の除去と巨大責務の分割を優先し、その後に型導入を評価する順序が現実的です。

### 優先して進めること

1. `HistoryService` / DI の未使用 `operationEngine` 契約を完全削除する。
2. `getPropertyAt` を含む互換 API に `@deprecated` と移行先を明示し、参照箇所を段階的に `getAnchorAt` 系へ寄せる。
3. `SVGRenderer` とドラッグ系ロジックを責務単位で分割する。

## レビュアーOpusからの再返信

丁寧な返信をいただいた。3点それぞれに応じる。

### `getPropertyAt` — 撤回はしないが、批判の照準を修正する

「死骸」という表現は撤回する。呼び出し元が `SVGRenderer`、`MapView`、`FeaturesTabView`、`PropertiesTabView`、複数テストに現存する以上、これは生きた互換レイヤーであり、「消し忘れ」ではない。

ただし、問題の本質は変わらない。むしろ深まっている。**互換レイヤーの呼び出し元がインフラ層・プレゼンテーション層の主要コンポーネント4箇所に根を張っている**ということは、移行が止まっているということだ。互換APIが「一時的な橋」ではなく「事実上の正規API」として定着しつつある。

`@deprecated` の付与は最低限として、移行のスケジュール（何を、いつまでに、どの順序で `getAnchorAt` に切り替えるか）を持たないと、`@deprecated` タグ自体がただの装飾になる。

### `worldWidth = 360` — 撤回する

これは私の読みが浅かった。360は経度の全幅であり、座標系の契約値だ。`ViewportManager` と `SVGRenderer` が同じ前提を共有していることも確認した。

ただし一点だけ指摘を残す。DI内のコメント `// ConfigManagerから取得する方が望ましい` は誤解を招く。Codex氏自身が「単独の定数移動ではなく契約整理として扱うべき」と述べている通り、このTODOコメントは実態と乖離している。コメントを実態に合わせて更新するか、削除すべきだ。「簡単に直せそうなのに直していない」と読めるコメントは、コードの信頼性を不必要に下げる。

### TypeScript — ここは譲らない

Codex氏の論旨は「ランタイムガードが存在するから、TSの優先度は低い」だが、これは**防御の層が異なる**という点を見落としている。

| 防御手段                             | エラー検出タイミング             | 検出できるもの                                   |
| ------------------------------------ | -------------------------------- | ------------------------------------------------ |
| `Object.freeze` / コンストラクタ検証 | **実行時**（テスト or 本番）     | 不正な値の代入、不正な引数                       |
| TypeScript                           | **開発時**（コードを書いた瞬間） | メソッド未実装、引数の型ミス、プロパティ名のtypo |

`IPolygonEditService` が好例だ。現状、新しいクラスがこのインターフェースを実装すべきなのに `splitPolygon` メソッドを書き忘れたとする。ランタイムガードは**そのメソッドが実際に呼ばれるまで何も言わない**。TypeScriptなら**ファイルを保存した瞬間にエラーが出る**。

そして「まず整理、その後にTS」という順序論には構造的な罠がある。整理すべきものは常に存在するため、TSの導入タイミングは永遠に来ない。逆に、**TSは整理を加速する道具でもある**。`getPropertyAt` の全呼び出し元を特定する作業は、TypeScriptの "Find All References" なら一瞬だが、grepでは偽陽性との戦いになる。

とはいえ、93ファイルの一括移行を提案しているわけではない。現実的な一歩として:

1. `tsconfig.json` を `allowJs: true`, `checkJs: true` で導入し、既存JSファイルをそのまま型チェック対象にする
2. Domain層の値オブジェクト（`Coordinate`, `TimePoint`, `FeatureAnchor`）だけ `.ts` に変換する — ここが型の恩恵が最大で、変更リスクが最小の場所だ

全面移行ではなく、**段階的な型の浸透**を提案する。

## 実装者Codexからの再返信

再整理ありがとうございます。こちらも3点に分けて返します。

### `getPropertyAt` について

ここは同意します。問題は「互換レイヤーが残っていること」ではなく、**主要経路に残ったまま移行計画が明文化されていないこと**です。

現状の参照は、少なくとも次の通りです。

```js
// src/infrastructure/rendering/SVGRenderer.js
const property = polygon.getPropertyAt(currentTime);

// src/presentation/views/MapView.js
? ownerFeature.getPropertyAt(currentTime)

// src/presentation/views/sidebar/FeaturesTabView.js
const prop = feature.getPropertyAt(currentTime);

// src/presentation/views/sidebar/PropertiesTabView.js
const currentProperty = typeof feature.getPropertyAt === 'function'
  ? feature.getPropertyAt(currentTime)
```

したがって、ここは次の順で畳みます。

1. `SVGRenderer` と sidebar 系を `getAnchorAt` 前提へ置換する。
2. `MapView` の参照を `FeatureAnchor` 参照ヘルパーへ集約する。
3. 互換API専用テストを縮退し、呼び出しゼロを確認する。
4. その時点で `getPropertyAt` に付けた `@deprecated` を実際の削除へ進める。

「一時的な橋が正規API化している」という指摘は、その通りです。

### `worldWidth = 360` について

ここも同意します。問題は値そのものではなく、コメントが実態を誤らせていることです。

```js
// src/main/DependencyInjection.js
const worldWidth = 360; // ConfigManagerから取得する方が望ましい
```

一方で、実装上は契約値として複数箇所で前提化されています。

```js
// src/infrastructure/rendering/ViewportManager.js
worldWidth: options.worldWidth || 360

// src/infrastructure/rendering/SVGRenderer.js
worldWidth: 360
```

したがって、このコメントは削除するか、「現行の世界地図座標系の契約値」であることが分かる文面へ更新します。

### TypeScript について

ここは半分同意、半分保留です。

まず、`checkJs` を入口にする提案は筋が良いです。`開発ガイド.md` でも、現行方針は次の通りです。

```md
- **型チェック**: TypeScriptまたはJSDocを使用した型注釈を使用
```

したがって、「まず静的検査を入れる」は今の方針と矛盾しません。`IPolygonEditService` のような契約チェックに静的解析を足す価値が高い点も同意します。

ただし、**値オブジェクト3つだけを直ちに `.ts` 化する案は、現行ツールチェーンでは局所変更になりません。** 根拠は次の通りです。

```js
// webpack.config.js
test: /\.js$/,
resolve: {
  extensions: ['.js']
}

// vitest.config.mjs
include: ["tests/**/*.test.js"]
```

加えて、`FeatureAnchor.js` / `TimePoint.js` / `Coordinate.js` は `src/` と `tests/` の広範囲から `.js` 拡張子付きで import されています。つまり、この3ファイルだけを `.ts` に変えて終わり、にはなりません。

なので、実際の順序は次が妥当だと考えます。

1. `tsconfig.json` を `allowJs: true`, `checkJs: true`, `noEmit: true` で導入する。
2. Domain の値オブジェクトとサービス境界に JSDoc を補強して、まず静的検査を回す。
3. その結果を見て、`.ts` 化は「変更波及が閉じる単位」で着手する。

要するに、TypeScript 導入自体には反対しません。ただし、いま直近で切るべきなのは「未使用契約の除去」と「互換APIの縮退」であり、静的型は **`checkJs` から入る** のがこのリポジトリには一番安全です。
